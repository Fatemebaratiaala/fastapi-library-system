# سامانه مدیریت کتابخانه با FastAPI و PostgreSQL

این پروژه یک API ساده برای ثبت، مشاهده، ویرایش و حذف کتاب‌هاست. داده‌ها در PostgreSQL ذخیره می‌شوند و دسترسی به پایگاه داده با SQLAlchemy انجام می‌شود.

## نیازمندی‌ها

- Python 3.10 یا جدیدتر
- PostgreSQL نصب‌شده و در حال اجرا (محلی یا سرور)
- یک پایگاه داده به نام `library_db` و کاربر/رمز معتبر

> فایل‌های پروژه را می‌توان بدون نصب PostgreSQL در Git قرار داد؛ اما برای اجرای API باید به یک PostgreSQL قابل‌دسترسی وصل شوید. اطلاعات اتصال محرمانه را در مخزن عمومی قرار ندهید.

## راه‌اندازی PostgreSQL

در PostgreSQL یک پایگاه داده بسازید (برای نمونه):

```sql
CREATE DATABASE library_db;
```

مقدار پیش‌فرض اتصال در `database.py` این است:

```text
postgresql://postgres:postgres@localhost:5432/library_db
```

آن را با متغیر محیطی `DATABASE_URL` مطابق کاربر، رمز، میزبان و پایگاه داده خود تغییر دهید. برای نمونه در Linux/macOS:

```bash
export DATABASE_URL='postgresql://USER:PASSWORD@localhost:5432/library_db'
```

در PowerShell ویندوز:

```powershell
$env:DATABASE_URL = 'postgresql://USER:PASSWORD@localhost:5432/library_db'
```

برای گذرواژه‌هایی که نویسه‌های ویژه دارند، آن‌ها را در URL به‌صورت URL-encoded بنویسید.

## نصب و اجرا

```bash
python -m venv .venv
# Linux/macOS
source .venv/bin/activate
# در Windows به‌جای خط بالا اجرا کنید: .venv\Scripts\activate
python -m pip install -r requirements.txt
uvicorn main:app --reload
```

سپس مستندات تعاملی را در [http://127.0.0.1:8000/docs](http://127.0.0.1:8000/docs) باز کنید. هنگام راه‌اندازی، جدول `books` در صورت نبودن ساخته می‌شود. این روش برای پروژه آموزشی مناسب است؛ برای پروژه واقعی، مهاجرت ساختار پایگاه داده را با Alembic مدیریت کنید.

## مسیرهای API

| روش | مسیر | کاربرد |
|---|---|---|
| `POST` | `/books/` | ایجاد کتاب (`title`, `author`, `published_year`) |
| `GET` | `/books/` | فهرست کتاب‌ها؛ پارامترهای `skip` و `limit` اختیاری‌اند |
| `GET` | `/books/{book_id}` | دریافت یک کتاب |
| `PUT` | `/books/{book_id}` | به‌روزرسانی فیلدهای ارسال‌شده |
| `DELETE` | `/books/{book_id}` | حذف کتاب |

در صورت نبودن شناسه، API پاسخ `404` می‌دهد.

## ORM در برابر Raw SQL

**ORM** (در این پروژه SQLAlchemy) اجازه می‌دهد جدول‌ها و رکوردها را با کلاس‌ها و اشیای پایتون مدل کنیم؛ برای نمونه `Book` متناظر جدول `books` است. این شیوه معمولاً خواناتر و نگه‌داری‌پذیرتر است، تبدیل داده‌ها را ساده می‌کند و با پارامترگذاری خودکار، خطر تزریق SQL را برای الگوهای معمول کاهش می‌دهد. بهای آن، یک لایه انتزاعی و گاهی کنترل کمتر بر SQL دقیق اجراشده است.

در **Raw SQL**، خودمان دستورهایی مانند `SELECT * FROM books WHERE id = %s` می‌نویسیم و مستقیماً اجرا می‌کنیم. این کار برای پرس‌وجوهای خاص یا کنترل دقیق مفید است، اما باید پارامترها را امن bind کرد (هرگز ورودی کاربر را با چسباندن رشته وارد SQL نکنید) و نگاشت نتیجه‌ها و مدیریت جزئیات پایگاه داده را نیز خودمان انجام دهیم. انتخاب روش به نیاز پروژه بستگی دارد؛ این نمونه برای سادگی و یادگیری از ORM استفاده می‌کند.
